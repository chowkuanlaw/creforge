# creforge v0.5: Fault Injection

**Status:** Draft for review
**Date:** 2026-09-27

## 1. Why

Data engineers need test data that is **wrong in known ways**, to prove that their
pipelines and data-quality checks catch problems before they reach reports, models or
regulators. Today people hand-craft a few broken rows, which covers little and can't be
measured. creforge already knows the exact truth of every row, so it can break a
dataset deliberately and say exactly what it broke. That turns a DQ test into a
measurable score: *my checks caught 94% of the injected faults, with 2 false alarms.*

## 2. How it works

A separate command takes a clean creforge dataset and writes a corrupted copy plus an
answer key. The clean dataset is left untouched, so users keep the ground truth.

```console
$ creforge generate -n 50000 -o clean
$ creforge inject clean --faults standard --seed 7 -o dirty
$ creforge score dirty/faults.parquet my_dq_findings.csv   # optional: grade your DQ checks
```

- `dirty/` has the same layout as a normal dataset, with every table and a manifest.
- `dirty/faults.parquet` is the **answer key**: one row per injected fault, listing the
  fault type, table, row key, column, original value and injected value.
- The same clean dataset, fault profile and seed always produce identical output.

A separate command was chosen over a `generate --faults` flag. It keeps the generator
simple, lets one clean dataset produce many dirty variants, and works on any creforge
dataset, including older ones.

## 3. Fault catalogue (v0.5)

| Group | Fault | What it does | Typical check that should catch it |
|---|---|---|---|
| Duplicates | `duplicate_row` | Exact copy of a row | Row-level uniqueness |
| | `duplicate_key` | Same primary key, different values | Primary-key uniqueness |
| Referential | `orphan_row` | `account_month` row whose account doesn't exist | Foreign-key check |
| | `missing_month` | A month deleted from the middle of an account's history | Contiguity / gap check |
| Values | `null_required` | A required column set to null | Not-null |
| | `unknown_code` | Enum value outside the allowed set (e.g. `dpd_bucket = "999"`) | Domain / allowed values |
| | `negative_amount` | Balance or payment made negative | Range check |
| | `scale_error` | Amount multiplied by 100 (cents vs units) | Outlier / distribution check |
| | `future_date` | `as_of_month` after the window, or `open_date` in the future | Date range check |
| | `code_formatting` | Codes with stray spaces or wrong case (`"Current "`) | Standardisation / trimming |
| Consistency | `dpd_jump` | Account jumps two or more DPD buckets in one month | Business rule: roll one bucket at most |
| | `paid_while_rolling` | Payment recorded in a month the account rolled worse | Business rule |
| | `activity_after_closure` | Rows after write-off or closure | Lifecycle rule |
| | `close_reason_mismatch` | `close_reason` disagrees with the final status | Cross-field rule |
| CSV only | `date_format` | Dates as `DD/MM/YYYY` in some rows | Parsing / schema check |
| | `type_mismatch` | Text in a numeric column (`"N/A"`) | Schema check |

Parquet enforces column types, so the two CSV-only faults apply only when the dirty
output is written as CSV. Late-arriving and restated records belong with the planned
monthly submission mode (feature C) and are out of scope here.

## 4. Fault profiles

Profiles are YAML, like the population profiles, with built-ins:

| Profile | Rate per fault type | Use |
|---|---|---|
| `light` | about 0.1% of eligible rows | Smoke-test that checks exist at all |
| `standard` | about 1% | Everyday DQ regression tests |
| `nasty` | about 5%, plus the rare combinations (several faults on one row) | Stress-testing robustness |

Custom profiles can set a rate per fault type, restrict faults to certain tables or
columns, or switch types off (`extends: standard` works as for population profiles).

## 5. Scoring (optional command)

`creforge score ANSWER_KEY FINDINGS` compares the answer key with a DQ tool's findings,
given as a CSV of `table, row key[, column]` in its simplest form. It reports recall
(share of injected faults found), precision (share of findings that are real) and a
breakdown by fault type. This makes "our DQ suite catches 94% of injected faults" a
repeatable number that can go in a pipeline's CI.

## 6. Guarantees and tests

- **Deterministic:** same input, profile and seed give byte-identical output (tested,
  as for `generate`).
- **Complete answer key:** every difference between clean and dirty is listed in
  `faults.parquet` and nothing else changes. A test diffs clean against dirty and checks
  them against the key.
- **`creforge validate` catches the structural faults:** a test injects each fault that
  `validate` covers and checks it's reported. That also dogfoods the feature.
- The dirty manifest records the fault profile, seed, and the clean dataset's
  `config_sha256`, so a dirty dataset can always be rebuilt.

## 7. Decisions for review

1. **Separate `creforge inject` command** rather than a `generate` flag (recommended,
   reasons in §2).
2. **Include `creforge score` in v0.5** (recommended: it's small, and it's the part that
   makes results measurable).
3. **Default rates:** `light` 0.1%, `standard` 1%, `nasty` 5%.

## 8. Out of scope (later)

- Late, duplicated and restated monthly submissions (with feature C).
- Schema drift across deliveries (renamed or added columns).
- Faults on `account_party` beyond duplicates and orphans.
