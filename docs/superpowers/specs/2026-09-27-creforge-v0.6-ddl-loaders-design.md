# creforge v0.6: Warehouse DDL and Loaders

**Status:** Draft for review
**Date:** 2026-09-27

## 1. Why

Every user's first hour is the same chore: writing `CREATE TABLE` statements for five
tables, getting the types right (decimals, dates, nullable columns) and loading the
files. creforge already knows the exact schema, so it should hand that over.

## 2. Commands

```console
# Table definitions for a warehouse, printed or written to a file
$ creforge ddl --dialect athena --location s3://my-bucket/creforge/ --database creforge_test
$ creforge ddl --dialect postgres --constraints -o schema.sql

# Load a generated dataset into DuckDB in one step
$ creforge load duckdb ./out --db creforge.duckdb
```

### `creforge ddl`

| Option | Meaning |
|---|---|
| `--dialect` | `athena`, `glue`, `duckdb`, `postgres`, `redshift`, `snowflake` |
| `--money` | `decimal` (default, `DECIMAL(18,2)`) or `float`, matching `generate --money` |
| `--format` | `parquet` (default) or `csv`: affects Athena/Glue storage clauses only |
| `--location` | S3 prefix for Athena/Glue external tables (`<prefix>/<table>/`) |
| `--database` / `--schema` | Qualify table names |
| `--constraints` | Add primary and foreign keys (Postgres, DuckDB; declared-only on Snowflake and Redshift, which don't enforce them) |
| `-o FILE` | Write to a file instead of printing |

Per dialect:

- **Athena:** `CREATE EXTERNAL TABLE … STORED AS PARQUET LOCATION …`. For CSV, uses the
  text SerDe with a header skip, and empty fields read as NULL.
- **Glue:** one Glue Data Catalog `TableInput` JSON per table, ready for
  `aws glue create-table --table-input file://…`.
- **DuckDB / Postgres / Redshift / Snowflake:** ordinary `CREATE TABLE` with that
  engine's types (for example `VARCHAR(13)` ids, `DATE`, `SMALLINT`, `DECIMAL(18,2)`,
  `DOUBLE PRECISION`/`FLOAT8`, `BOOLEAN`).

Enum columns become `VARCHAR`. With `--constraints` on Postgres and DuckDB they also get
`CHECK (col IN (…))` from the profile, so the database itself rejects
`creforge inject`'s unknown codes.

### `creforge load duckdb`

Creates the tables (with constraints off by default, so dirty datasets load too) and
loads every part file with DuckDB's native Parquet/CSV reader. It needs the optional
extra `pip install creforge[duckdb]`. Postgres users get the DDL plus a generated
`\copy` script (`creforge ddl --dialect postgres --copy-script ./out`), because
loading over a network connection belongs to their own tooling.

## 3. One schema source

A new internal module describes each column once: its logical type (id, text, code,
date, int16, money, rate, bool), nullability and key role. The DDL for every dialect is
generated from it. A test checks that this description matches real generated output,
column for column, the same way the data dictionary is already checked.

## 4. How it's tested

| Dialect | Test |
|---|---|
| DuckDB | Run the DDL, load a generated dataset, and check row counts and types; also load a dirty (injected) dataset. |
| Postgres | CI starts a real Postgres (GitHub service container), runs the DDL with `--constraints`, loads a small dataset with the `\copy` script, and checks row counts. It also checks that constraints reject an unknown code. |
| Athena, Glue, Redshift, Snowflake | Snapshot tests of the generated SQL/JSON, plus review against each engine's documented syntax. **Not executed against the real engines in CI**, and the docs say so plainly. |

## 5. Decisions for review

1. **Six dialects** as listed. Athena/Glue for your stack; Postgres/DuckDB are the most
   common local targets; Redshift/Snowflake cover the other big warehouses.
2. **Loader for DuckDB only** in 0.6 (optional dependency); Postgres gets a `\copy`
   script rather than a network loader.
3. **Constraints off by default**, so dirty datasets load; `--constraints` turns them
   on.
