# creforge v0.7: Monthly Submissions

**Status:** Draft for review
**Date:** 2026-09-27

## 1. Why

A real bureau never receives a clean five-table dataset. It receives **one file per
lender per month**, and those files arrive late, twice, out of order, or get corrected
weeks later. The ingestion pipeline has to rebuild the true picture from them: take the
latest correction, ignore duplicates, slot late months into the right place. That logic
is where many bureau data bugs come from, and today nobody can test it with realistic
data.

creforge already has the truth (the clean dataset). v0.7 turns it into the stream of
monthly submissions a bureau would have received, with delivery problems injected, and
checks whether the user's pipeline rebuilds the truth.

## 2. Commands

```console
$ creforge generate -n 50000 -o clean
$ creforge submissions clean --issues standard --seed 7 -o inbox
$ #  ... the user's pipeline ingests inbox/ in arrival order into its own tables ...
$ creforge reconcile clean rebuilt/          # did the pipeline rebuild the truth?
```

### `creforge submissions CLEAN -o INBOX`

Splits a clean dataset into submission files, one per lender per reporting month:

```
inbox/
  submissions.parquet                      # the delivery log (see below)
  L0007/2024-03/S000123.parquet            # lender / reporting month / submission id
  L0007/2024-04/S000131.parquet
  ...
```

Each file is what a lender sends for one month: one row per account it reports that
month, with the account's static fields (`product_type`, `open_date`, `credit_limit`, …)
and that month's status fields (`balance`, `amount_paid`, `dpd_bucket`, `status`, …).
This is the flattened "account + month" record that real bureau formats use.

`submissions.parquet` is the delivery log: `submission_id`, `lender_id`,
`reporting_month`, `received_at` (timestamp), `kind` (`original`, `correction`,
`resend`), `row_count` and `file`. A pipeline should process files in `received_at`
order, exactly as it would in production.

Options: `--issues` (profile, default `none`), `--seed`, `--format parquet|csv`.

### `creforge reconcile CLEAN REBUILT`

Compares the `account` and `account_month` tables a pipeline rebuilt (a directory of
Parquet/CSV files, or a DuckDB file) with the clean truth. It reports missing rows,
extra rows and wrong values per column, and exits non-zero on any difference
(`--max-mismatch` to allow some). The report names the delivery issue that caused each
difference, so "you applied the original instead of the correction for account X in
March" is visible directly.

## 3. Delivery issues

| Issue | What happens | What the pipeline must do |
|---|---|---|
| `late` | A month's file arrives after the next month's file | Place data by `reporting_month`, not arrival order |
| `duplicate` | The same file is sent again under a new `submission_id` (`kind = resend`) | Deduplicate; don't double-count |
| `correction` | The original file carries wrong values for some accounts (for example `amount_paid`, `dpd_bucket`, `status`); a later `correction` file restates those accounts with the true values | Latest correction wins, per account and month |
| `missing_then_catch_up` | A lender skips a month, then sends two months in its next delivery | Accept both months; don't flag the gap as permanent |
| `partial` | A file contains only part of the lender's accounts; the rest arrive in a follow-up file for the same month | Merge both parts |
| `out_of_order_correction` | A correction arrives before the original it corrects | Don't let the older original overwrite the correction |

The corrected values are always the true ones: applying every file correctly rebuilds
the clean dataset exactly. That gives `reconcile` a precise answer.

Issue profiles are YAML like the fault profiles, with built-ins `none` (clean monthly
files, useful on their own), `light`, `standard` and `nasty`. The existing record-level
faults (`creforge inject`) can be applied first to test both layers together.

## 4. Guarantees and tests

- **Deterministic:** same clean dataset, profile and seed give byte-identical files.
- **Lossless:** a reference ingester in the test suite (latest `received_at` wins per
  account and month, resends dropped) rebuilds the clean `account` and `account_month`
  tables exactly, for every built-in profile. The same ingester, run naively (arrival
  order, no dedup), must fail `reconcile`, proving the issues are real.
- The delivery log lists every file, and every issue is recorded in an answer key
  (`inbox/issues.parquet`), like `faults.parquet`.

## 5. Decisions for review

1. **Separate `creforge submissions` command** working on any clean dataset (like
   `inject`), rather than a `generate` flag.
2. **One flattened account+month record per row** in submission files, instead of
   separate account and account_month files. It matches real bureau formats and makes
   corrections simple. `subject`, `inquiry` and `account_party` stay out of scope for
   0.7.
3. **Include `creforge reconcile`**, so the result is a pass/fail check that fits in CI.
