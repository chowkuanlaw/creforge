# creforge v0.8: Scorecard Feature Table

**Status:** Draft for review
**Date:** 2026-09-27

## 1. Why

The most common use of bureau data is a credit score. Every modelling team rebuilds
the same thing first: one row per borrower as of an observation date, a set of
bureau-style attributes, and a good/bad flag over the following months. Getting that
right is hard in practice: data from after the observation date leaks into the
features, bad definitions are inconsistent, and exclusions are forgotten.

creforge knows every borrower's true risk grade and full history, so it can produce a
**leakage-free, point-in-time feature table with a correct target**. Model builders
then get a realistic training set, and feature-pipeline builders get a reference
answer to test their own SQL against.

## 2. Command

```console
$ creforge features clean --as-of 2024-06 --performance 12 -o features.parquet
$ creforge features clean --as-of 2024-03 --as-of 2024-06 -o features/   # several snapshots, for out-of-time tests
```

| Option | Meaning |
|---|---|
| `--as-of YYYY-MM` | Observation month (repeatable). Features use data up to the end of this month only. |
| `--performance N` | Months after the observation month in which the target is measured (default 12). |
| `--bad` | Bad definition: `90dpd` (default: 90+ days past due or written off in the window), `60dpd`, or `writeoff`. |
| `--include-truth` | Add the hidden `risk_grade` (the generator's truth) for model diagnostics. Off by default, because a real bureau has no such column. |
| `-o` | Output file (one snapshot) or folder (one file per snapshot). |

The observation month must leave room for the whole performance window inside the
dataset; the command says so if it doesn't.

## 3. The table

One row per subject with at least one account open at the observation month.

| Group | Features (all computed from data up to the observation month) |
|---|---|
| Portfolio | Open accounts, by product; secured share; total balance; total credit limit |
| Utilisation | Revolving utilisation (balance / limit on cards and overdrafts); maximum single-account utilisation |
| Delinquency | Worst DPD bucket now and in the last 3, 6, 12 and 24 months; months since last delinquency; number of accounts ever 30+, 60+ and 90+ |
| Payment | Payment-to-due ratio over the last 3 and 6 months |
| History | Age of oldest and newest account; months on file |
| Demand | Inquiries in the last 3, 6 and 12 months; accounts opened in the last 12 months |
| Links | Number of accounts held as joint holder or guarantor |
| Target | `bad` (0/1) per `--bad`, and `bad_month` (the first bad month, or null) |

Standard **exclusions**, flagged rather than silently dropped so users can apply their
own policy: `excluded = already_bad` (90+ DPD or written off at the observation month)
or `no_open_account`. They are all listed in the data dictionary.

## 4. Guarantees and tests

- **No leakage:** a test changes every row after the observation month (and every
  inquiry after it) and checks that no feature changes. Only `bad` and `bad_month` may
  change.
- **Target correct:** the target is recomputed independently from `account_month` in
  the tests.
- **The data carries signal:** a plain logistic regression on the features (in the
  tests, with no extra dependencies: a few lines of numpy) must reach a Gini
  coefficient clearly above zero, with bad rates increasing monotonically with the
  hidden risk grade. That proves the generator's risk ordering survives into the
  features without claiming any real-world accuracy.
- **Deterministic** and streaming: computed chunk by chunk, since subjects never cross
  chunks.
- A reference SQL (DuckDB) for a few features in the docs, tested for equality with
  the Python output, so users can compare their own warehouse code.

## 5. Decisions for review

1. **Default bad definition: 90+ DPD or written off within 12 months**, the usual
   industry and Basel default definition, with `60dpd` and `writeoff` as options.
2. **Exclusions flagged, not dropped** (recommended, so the user controls the policy).
3. **Hidden risk grade only with `--include-truth`**, so the default output looks
   like a real bureau extract.
4. **About 30 features** as listed. More can be added in minor versions (new columns at
   the end, per the stability policy).
