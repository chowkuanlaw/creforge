# creforge 1.0: Stability Release

**Status:** Draft for review
**Date:** 2026-10-07

## 1. What 1.0 means

From 1.0, the promises in [docs/stability.md](../../stability.md) take effect: no breaking
change to the schema, commands or Python API without a major version (2.0). 1.0 adds
**no new features**. It is the last chance to fix names and formats cheaply, and the
point where users can depend on creforge in their own pipelines and CI.

| Check | Result |
|---|---|

| Python 3.10 | Reaches end of life this month (October 2026) |
| Open issues | None |

## 3. What becomes a contract

Today `stability.md` covers the five tables, the manifest, the CLI commands and the
Python API. 1.0 extends the same rules to the formats added in 0.5–0.8, because users
will build on those too:

| Contract | Documented in |
|---|---|
| Five tables and `manifest.json` (schema version 3) | data dictionary (already) |
| Fault answer key `faults.parquet` and the findings format for `score` | fault-injection.md |
| Submission files, delivery log `submissions.parquet`, answer key `issues.parquet` | submissions.md |
| Feature table columns, bad definitions and exclusion values | features.md |
| DDL type mapping per dialect (the SQL text itself may be reformatted) | warehouses.md |
| JSON output of `validate`, `score` and `reconcile` (keys may be added, never removed) | each command's docs |

Not contracts: Markdown report text, log messages, and anything not importable from
`creforge`.

## 4. Last-chance API fixes

Small inconsistencies that would otherwise be frozen. Each becomes a breaking change
after 1.0, so this is the moment.

| Now | 1.0 | Why |
|---|---|---|
| `inject(clean, out, …)` | `inject(dataset, out, …)` | Every other function calls its input `dataset` |
| `feature_columns(products)` | `feature_columns(profile="baseline")` | The caller shouldn't have to dig out the product list |
| `format: str \| None` in `inject` and `submissions` | `Literal["parquet", "csv"] \| None` | Type checkers then catch typos |
| `validate(data)` | `validate(dataset)` | Same naming |

The old keyword names keep working in 1.0 with a `DeprecationWarning`, and are removed
in 2.0, following the deprecation policy.

## 5. Platform

- **Python 3.11–3.14.** Add 3.14 to the CI matrix and drop 3.10, which is end of life.
- **Dependencies:** keep the tested minimums (Polars ≥ 1.0 …). Add Polars 2.x to the
  CI matrix explicitly, so both major lines stay tested.
- **Weekly scheduled CI run** against the newest dependency releases, so a breaking
  upstream release is caught within a week rather than by a user.
- Classifier `Development Status :: 5 - Production/Stable`.

## 6. Same data as 0.8

1.0 makes no change to the generator. A release check generates a dataset with the
published 0.8.0 and with 1.0.0, from the same seed, and confirms the files are
byte-identical. The CHANGELOG then says: *datasets from 0.8 reproduce exactly in 1.0*.

## 7. Release

- CHANGELOG 1.0.0 with an "Upgrading from 0.x" section (renames, Python 3.10 dropped).
- README: a "Stable since 1.0" note linking to the stability policy.
- Publish 1.0.0 directly, without a release candidate: there are no known external
  users yet, so a release candidate would collect no feedback.

## 8. Decisions for review

1. **Drop Python 3.10** at 1.0 (it is end of life this month); support 3.11–3.14.
2. **Make the four API fixes** in §4, with deprecation warnings for the old names.
3. **Extend the contract** to the 0.5–0.8 formats (§3).
4. **Release 1.0.0 directly**, with no release candidate.
